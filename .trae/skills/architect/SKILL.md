# 架构设计技能

## 描述
根据产品需求进行系统架构设计，输出标准化的设计文档、技术选型分析和 API 契约。

## 何时使用
- 项目启动阶段，需要从零设计系统架构
- 新增核心功能模块，需要设计模块间交互
- 技术选型需要评估和决策
- 现有架构需要重构或扩展

## 指令

### 第一步：需求分析
1. 仔细阅读用户提供的需求描述
2. 识别核心功能模块和业务实体
3. 梳理模块间的依赖关系和数据流
4. 识别非功能性需求（性能、安全、可扩展性）

### 第二步：架构设计
1. 设计系统整体架构（分层、模块划分）
2. 设计模块间的通信方式（REST API、事件驱动等）
3. 设计数据模型和存储方案
4. 识别关键设计决策并说明理由

### 第三步：技术选型
1. 根据需求评估候选技术方案
2. 从以下维度对比：
   - 社区活跃度和生态
   - 学习曲线和团队适配
   - 性能和可扩展性
   - 长期维护成本
3. 输出选型结论和理由

### 第四步：输出文档
将设计结果输出到以下文件：

| 文件 | 路径 | 格式 |
|------|------|------|
| 架构文档 | `docs/architecture.md` | Markdown + Mermaid |
| API 契约 | `docs/api-contract.yaml` | OpenAPI 3.0 YAML |
| 技术选型 | `docs/tech-stack.md` | Markdown |

## 输出格式要求

### 架构文档（architecture.md）
```markdown
# 系统架构设计

## 1. 概述
## 2. 系统架构图（Mermaid）
## 3. 模块设计
## 4. 数据模型
## 5. 关键设计决策
## 6. 风险与缓解
```

### API 契约（api-contract.yaml）
- 使用 OpenAPI 3.0 规范
- 包含完整的 paths、components/schemas、components/responses
- 每个端点包含请求参数、响应格式、错误码定义

### 技术选型（tech-stack.md）
```markdown
# 技术选型

## 选型矩阵
## 各技术方案对比
## 最终选型及理由
## 版本要求
```

## 注意事项
- 不编写业务代码，只输出设计文档
- 架构图使用 Mermaid 语法，确保可渲染
- API 契约必须完整，可供前后端 Agent 直接使用
- 设计决策需要说明"为什么"而不是只写"是什么"
